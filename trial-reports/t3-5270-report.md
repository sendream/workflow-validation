## 1. Task, route, and final disposition

Issue `#5270` demonstrates quadratic formatting time for a long chain of consecutive subscripts. The binding behavior contract required all of the following at once:

- use the issue generator at n=40,80,160,300;
- make n=160 at least 10x faster and remove n300's quadratic growth;
- preserve complete formatted bytes at all four sizes;
- preserve all pre-existing formatter fixture output and the full suite;
- run a real falsification-first Role Reviewer before delivery.

The session classified the task as `high / file-linked / complex-task path`. This was the correct route: several candidates met the timing target and passed focused tests, the fixture corpus, and the full suite, yet the isolated reviewer repeatedly found valid output drift outside the original test matrix.

The hard contracts ultimately conflicted for the attempted direct-batching design. The fastest candidate exceeded the required speedup by a wide margin, but output equivalence could not be established over Black's accepted syntax domain. Per the task card, the implementation stopped instead of weakening output identity. Commit `1ac5227` reverts the complete product experiment, so the final product tree is byte-identical to the task base. The branch is delivered as an auditable partial investigation, not as a fix.

No bare control arm was run because T3 explicitly excluded one. No branch was pushed to `psf/black`, no PR was opened, and no upstream issue comment was made.

## 3. Candidate history and falsification

### Candidate 1 — `d522def`

The first implementation added an atomic one-pass constructor for a narrow direct-assignment RHS made from a NAME base and simple subscript bodies. Its evidence appeared strong: n160 was about 84x faster, real split calls flattened, all four issue-generator outputs matched, and the full suite passed.

The isolated reviewer blocked it with three direct findings:

1. Annotated assignment drift: `result: list[int] = a` plus 60 simple NAME subscripts produced 598 candidate bytes versus 592 legacy bytes.
2. The work assertion `large <= small * 4` allowed exact quadratic growth at equality.
3. The fixture comparator collapsed four duplicate loader entries by using a non-unique key, overstating corpus identity.

All findings were accepted. The work oracle was strengthened and corpus comparison changed to duplicate-preserving signatures.

### Candidate 2 — `5757101`

The partition crossing boundary was adjusted and decreasing trailer widths were rejected. A second isolated review found a monotonic increasing-width CJK STRING chain that still changed output: 527 candidate bytes versus 509 legacy bytes, with 89 mismatches among 669 accepted cases. STRING bodies were removed from the fast-path grammar.

### Candidate 3 — `4af4863`

A controller-side falsifier immediately found the same class for increasing-width CJK NAME bodies. This candidate was rejected before review completion; NAME/NUMBER spellings were restricted to ASCII.

### Candidate 4 — `483b25d`

The next exact-SHA review found custom-line-length drift: optional RHS parentheses differed when the assignment/RHS prefix hit a layout boundary. Exact examples reproduced at line lengths 10 and 17. The focused test covered only one base spelling and did not prove the accepted domain.

### Candidate 5 — `1ff3445`

An equality guard was added, and the candidate still achieved n160 speedup of 60.71x with an observed n160-to-n300 exponent of 0.812. Required issue-generator bytes, duplicate-safe corpus comparison, focused tests, and the full suite were GREEN.

The same isolated reviewer nevertheless returned a valid blocking result:

- the exact prior `result = base` case at line length 10 still entered the helper four times and produced 284 candidate bytes versus 518 legacy bytes;
- a 2,520-case mutation of RHS bases, LHS names, and annotations found 53 mismatches among 490 accepted cases, including default-line-length drift;
- the submitted 3,920-case matrix was exhaustive only over fixed ASCII surrounding spellings, not the accepted syntax domain.

### Final controller falsification

Two broader probes confirmed this was not a one-condition tail bug:

- a 6,020-case surrounding-context scan found five output mismatches after the attempted follow-up guards;
- a 625-case LHS/base-width matrix accepted 239 cases and found 133 candidate-versus-legacy byte mismatches among those accepted cases.

The latter acceptance/mismatch ratio was the stop signal. Continuing to add syntax and width guards would produce an overfit parallel layout engine whose safety depended on enumerating Black's formatting semantics. That violates the task's output-identity priority.

## 7. Workflow mechanisms actually consumed

### Materially useful

- Project knowledge supplied the correct `env -u NO_COLOR` acceptance command and prevented the Step 1 environment failure from being misclassified as a code regression.
- G09 separated performance, exact bytes, corpus identity, and fallback behavior into independent blocking observables.
- The three root files were genuinely maintained. They preserved the baseline protocol, recorded rejected paths, reopened candidates after review, and stopped stale GREEN evidence from becoming delivery evidence.
- One isolated qa Role Reviewer was reused across four exact-SHA blocking reviews with `subdelegation=none`. It found distinct annotation, literal/display-width, optional-parenthesis, and surrounding-context compatibility classes that focused tests, corpus fixtures, and full suites missed.
- The falsification-first pass contract prevented a zero-cost approval. The final result remained blocking, which directly caused the unsafe product patch to be withdrawn.
- Duplicate-preserving evidence repair exposed a real 972-to-968 key collapse rather than allowing a broad but false corpus-clean claim.
- G20's known linked-worktree warning was resolved through the standing ruling and independent `git check-ignore --no-index`, without modifying workflow files.

### Cost and friction

- This high route was expensive. The isolated implementation thread alone used about 50.5 minutes and more than 17 million mostly cached input tokens before controller probes and reviewer cycles.
- Direct batching produced a long guard-narrowing loop. The trajectory monitor did not warn because the failure pattern alternated tests, edits, and new evidence rather than repeating an identical command or editing one file five times without a recognized verification command.
- Evidence paths needed compatibility copies for strict closeout lookup during an earlier candidate; this is trial friction, not product evidence.
- The packet result schema required a blocking finding to carry a reproduced falsifier while `falsification_attempts.outcome` itself uses exclusion-style values.
- Optional Ruff was unavailable and was never claimed as PASS evidence.

## 9. Final conclusion

T3 did not produce a safe fix, and the branch must not be represented as one. It did produce high-confidence evidence about the defect, the direct-batching failure mode, the limits of the existing corpus, and the behavior of two upstream alternatives on the frozen baseline.

Most importantly, the workflow changed the delivery outcome: without the high-tier falsification loop, at least three fast, full-suite-green candidates would likely have been shipped despite formatting drift. The correct result under the user's contract is therefore partial completion with no product change, not a superficially successful optimization.
